# Optional personal Grafana Cloud telemetry

`ny.vps.observability` is disabled by default (`vps_observability_enabled: false`). No Grafana, Loki or Prometheus server runs on this VPS. Dashboards and ruler alerts live in `observability/`, ready for import into the owner's personal Cloud tenant. No backup widgets or backup schedules are included; keep the existing OVH backup.

## Private setup and failure isolation

Supply these values through the operator's private environment or Ansible Vault, never Git, command arguments, CI output or reports:

- `GRAFANA_CLOUD_METRICS_URL` and `GRAFANA_CLOUD_METRICS_USERNAME`
- `GRAFANA_CLOUD_LOGS_URL` and `GRAFANA_CLOUD_LOGS_USERNAME`
- `GRAFANA_CLOUD_TOKEN` (personal tenant token scoped only for metrics/logs write)

Use the exact HTTPS endpoints from that tenant. The role rejects missing/invalid values before installation, masks secret tasks and writes only root-owned `/etc/alloy/cloud.env` (`0600`, parent `0700`). The Alloy configuration references environment variables, never literal credentials. Never use `--diff` to inspect the private file manually. Invalid cloud authentication affects only telemetry: no task, handler or systemd relationship restarts Docker/Caddy/apps because Alloy fails.

Run `make check` and, with local Docker available, `make observability-check` (official digest-pinned Alloy config validation plus synthetic redaction test; no cloud/network/private runtime mounts). Review local checks, provide private inputs, then run `make observability TARGET=vps-d9d9aca9`, which invokes only `playbooks/observability.yml`. This collector-only entry point validates private inputs before any mutation and includes no Docker/Caddy package roles or application restart handlers. Use `ansible-playbook -i inventories/production/hosts.yml playbooks/observability.yml --limit vps-d9d9aca9 -e vps_observability_enabled=true --tags observability_preflight` for a private input-only check. `platform.yml` no longer includes the collector; explicit platform maintenance remains separate. The role installs and holds official `alloy=1.21.3-1` from the signed Grafana APT repository; package auto-start is suppressed. Alloy validates the candidate config before replacement and again before service start. Diagnostics listen only on `127.0.0.1:12345`. Service restarts occur only after successful config validation. A cloud 401/403 cannot be proven locally: check remote-write health privately after deployment.

Alloy is a trusted root host service: cAdvisor needs cgroup/runtime access, and Docker socket access is already root-equivalent. Deploy identities gain none of these permissions. The collector has a read-only system filesystem view, no home access, no-new-privileges, 25% of one CPU, CPUWeight 64, MemoryHigh 256 MiB, MemoryMax 384 MiB, no swap, TasksMax 128, and GOMEMLIMIT 192 MiB. A private 128 MiB tmpfs bounds WAL/cache storage; it is charged to collector memory and discarded on restart/reboot. Remote-write uses one shard, a 2500-sample queue and at most 15 minutes of WAL retention. Disk cannot grow indefinitely during an outage; data may be lost when bounds are reached. This favors production capacity over telemetry durability.

The read-only `vps-platform-metrics.timer` writes platform counts/reservations and reboot-required to a textfile once per minute. It reads the registry without credentials, never calls Docker, and has independent 32 MiB/5% CPU limits. Retired state reserves no compute; its disk budget remains visible. `node_reboot_required` reflects `/var/run/reboot-required` (it does not invent a distro signal). A missing/corrupt registry emits `vps_platform_collect_success=0`.

## Collection and export limits

Host metrics use a selected node-exporter collector set; cAdvisor keeps one minute of CPU/memory state, exporting managed applications only. Application, environment (`prod`, `staging`, `preview`) and service are low-cardinality labels. PR numbers, container IDs, image digests and arbitrary container labels are removed before export. HTTP probes run every minute for the four fixed production endpoints with normal TLS verification, five-second timeouts and no redirects. Probe status codes include auth/404 endpoints as reachable; these remain availability probes, separate from actual request measurements.

Application container logs and selected Caddy/Docker/platform journal messages share one processing pipeline before remote export: lines over 4 KiB and lines containing credential markers are dropped, email addresses are redacted, only warning/error/fatal/panic/critical/failed diagnostics remain, and a global token bucket allows one line per second with a burst of ten. This bounds exported log payload to about 338 MiB/day plus labels/protocol overhead. Loki WAL is disabled and retries are limited. Collection is best effort and drops during overload/outage. Docker source logs already rotate at 10 MiB × 3 per container and the host journal is capped separately.

Secret filtering cannot recognize arbitrary unmarked application data. Validate synthetic examples and privately review real diagnostics before enabling export; applications must not write secrets or private content to logs. For a stricter application policy, exclude its source rather than adding high-cardinality identifiers. None of the registry, Compose, Docker environment variables, HA settings or content databases is exported.

## Dashboard and alert import

Import the three dashboard JSON files via Grafana's dashboard import, mapping `DS_PROMETHEUS` to the personal Cloud metrics source. Import `observability/alerts/personal-vps.yml` into that tenant's Prometheus/Mimir ruler namespace using the Cloud alert-rule UI/API. It is standard ruler YAML, not Grafana-managed alert provisioning YAML. Review the labels and provision a personal contact point/notification policy in Cloud; repository files do not activate notifications by themselves.

Rules cover missing host telemetry, production HTTP probe failures, actual 5xx responses, memory/CPU/disk/inode pressure, non-ready production registry state, missing registry metrics and reboot-required. Missing host telemetry is evaluated remotely, so a stopped VPS/collector can alert. Import does not test email delivery; send a test notification from the personal account. Dashboard queries assume the default host label `personal-vps`; update the definitions together if it changes.

## Verification and recovery

On the host, privately check `systemctl status alloy vps-platform-metrics.timer`, `curl -fsS http://127.0.0.1:12345/-/ready`, `/run/alloy-platform/platform.prom`, and collector health. Confirm the endpoint is not reachable publicly. In Cloud confirm fresh host/container/HTTP metrics, bounded labels, filtered synthetic logs and rule evaluation. Capture metric freshness and route/data checks before and after enabling.

To stop telemetry independently: `sudo systemctl disable --now alloy vps-platform-metrics.timer`. Set `vps_observability_enabled=false` to avoid future configuration; that flag deliberately makes the role a no-op and does not stop a previously installed collector. Rotate a token only through the private input and role. Keep last known-good private config/environment outside Git before changing them. A rejected Alloy candidate never restarts production; repair/revert its private config and restart only Alloy. Telemetry tmpfs is intentionally disposable and never contains application data.

Official references: [Linux installation](https://grafana.com/docs/alloy/latest/set-up/install/linux/), [cAdvisor](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.exporter.cadvisor/), [remote write/WAL](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.remote_write/), [Loki processing](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.process/), [HTTP exporter](https://grafana.com/docs/alloy/latest/reference/components/prometheus/prometheus.exporter.blackbox/). Rendered config was validated with official `grafana/alloy:v1.21.3`; live Linux/systemd, Cloud ingestion and notification delivery remain rollout checks.


## Actual request traffic, errors and latency

The controller-generated Caddy JSON enables bounded global metrics with `per_host` disabled. The pinned 2.11.7 version automatically allows HTTPS Host labels even with `observe_catchall_hosts=false`, so per-host metrics are deliberately avoided. No strict SNI/Host behavior or legitimate application routing changes are introduced.

Before enabling collection, install the updated controller and verify `/var/log/caddy` is owned by `caddy:caddy` with mode `0700` (both controller and ingress roles manage it before maintenance; the controller also prepares the fixed directory before each logging configuration load), then use the private `sudo vpsctl ingress refresh` command to load the generated source logging configuration. This is an explicit atomic configuration refresh; it does not run package roles or restart applications. Keep the previous private Caddy JSON for recovery. Verify public production routes/HA connectivity as usual. Do not invoke `platform.yml` just to enable the collector; its maintenance package roles are separate.

Caddy maps only registered routes to static app/environment loggers. It drops the whole request object and response headers at the source encoder and writes private `0600` JSON to `/var/log/caddy/vps-http.json`, capped at 10 MiB with two rotations. Unknown hosts produce no access record, and the default runtime logger excludes access logs. Static application/environment fields remain with numeric HTTP status and duration; URI, query, host, client IP, user ID and credentials are absent.

Alloy reads that file locally, validates the fixed three-application allowlist, environment and three-digit status labels, then emits `vps_http_requests_total` and `vps_http_request_duration_seconds_{bucket,count,sum}`. There are no URI, host, container, method or filename label dimensions. Only these selected numeric metrics are scraped from Alloy's existing loopback endpoint and sent to Cloud. The access-record pipeline has no log-export receiver. Diagnostic log redaction/rate limits remain independent and do not sample request metrics.

The HTTP dashboard shows actual traffic/status counts, 500/503 rates, 5xx fraction and p50/p95 latency from collected requests. The alert uses the Caddy server-event timestamp of the most recent 5xx, so an isolated first error is visible on the first metric observation, including after a collector reset or idle-series recreation. It fires while that event is between zero and five minutes old, without an additional pending delay, then resolves. Old buffered events do not become new failures when ingested later. Blackbox checks remain separate. Like the rest of bounded telemetry, metric collection can lose data during outages, overload or file rotation. Counter state resets on Alloy restart; source positions are bounded/disposable and `tail_from_end` avoids replaying historical access records as current traffic. No requests predating collector startup are backfilled.

Run `make http-metrics-check` with local Docker to validate the pinned Caddy config and make real 200/500/503 requests through a proxy, including private headers/query strings and unknown hosts. The fixture checks source privacy, exact unduplicated status counts, histograms and low-cardinality labels with the pinned official Alloy binary, without publishing ports. Official Caddy references: [metrics](https://caddyserver.com/docs/metrics), [logging](https://caddyserver.com/docs/json/logging/), [API](https://caddyserver.com/docs/api).


## Recent-error and bridge freshness semantics

`vps_http_last_error_timestamp_seconds` is a gauge set only by 5xx records using the existing source-sanitized Caddy `ts` value. It has the same bounded application/environment/status labels and 24-hour idle retention as the request metrics and passes the explicit numeric export filter. The alert evaluates server event age, not scrape/ingestion time. The HTTP dashboard shows its age plus raw request counters; rate/increase panels still require observed counter changes and can omit a series' initial burst. A restart resets metric state and starts at the current file end, so only newly collected errors are reported after startup. Overload/outage loss limits remain unchanged.

`vps_platform_last_collection_timestamp_seconds` records whole epoch seconds when the one-shot bridge renders a replacement file. It advances on collector execution/write, never when Alloy re-scrapes an old file. Registry monitoring retains explicit `collect_success=0` and missing-series conditions, and additionally detects a write timestamp older than three minutes or a missing timestamp (including legacy success-only files). Its existing five-minute pending period is retained; a stalled bridge therefore alerts about eight to nine minutes after its last write. A fresh successful replacement resolves it. The host dashboard shows bridge write age; a healthy host scrape alone does not establish registry collector freshness.

Run `make monitoring-rules-check` for official promtool behavioral tests covering first isolated/subsequent 5xx, idle recreation, collector reset, old buffered events, expiration, stalled bridge writes despite success=1/fresh host samples, normal refresh, explicit failure, missing series and recovery. `make http-metrics-check` additionally sends the gauge through the actual selection/remote-write path into a local official Prometheus receiver, compares it to Caddy's event time, and exercises accelerated fixture-only idle eviction/recreation and an actual collector restart. Its local textfile bridge input also proves that freshly scraped samples preserve the old write timestamp until another bridge write.
